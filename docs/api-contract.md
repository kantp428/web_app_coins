# Authentication contract (F02)

POST /auth/login: JSON `{ "username": "0000000000000", "password": "...", "role": "CUSTOMER" }`. Roles: CUSTOMER, SELLER, GOVERNMENT. Customer username must contain exactly 13 ASCII digits; other usernames are 1–255 characters. Password 1–1024 characters.

200: `{ "accessToken": "<JWT>", "expiresIn": 3600, "user": { "id": "1", "role": "CUSTOMER", "displayName": "..." } }`. 400 invalid input; 401 incorrect credentials, inactive account or role mismatch; 503 missing JWT configuration. IDs are strings. Login responses must not be cached.

GET /me: `Authorization: Bearer <JWT>`. 200 user profile with id, role, displayName; 401 missing/invalid/expired token or inactive account/changed role.

Web POST /api/auth/login forwards login to API and sets session cookie (HttpOnly, SameSite=Lax, Secure in production, 3600 seconds). Returns destination /wallet, /store or /government. Web POST /api/auth/logout returns 200 JSON `{ "message": "Logged out" }` and clears cookie; signed JWT expires naturally (no server revocation). Both require same-origin Origin header. Configure server-only API_URL for web and DATABASE_URL/JWT_SECRET for API.

Accounts use scrypt hashes documented in decisions.md. Demo seed credentials are documented in Test.md.

## Registration

POST /auth/register: common fields `role`, `username`, `password`, `confirmPassword`. Customer username is 13 ASCII digits; seller/government username is 3–64 ASCII letters/digits/underscore/dot/hyphen. Password 8–128 characters and confirmation must match.

- CUSTOMER requires `firstName` (trimmed 1–100 chars) and `lastName` (1–99 chars); joined into users.display_name. Example: `{ "role": "CUSTOMER", "username": "0000000000001", "firstName": "Test", "lastName": "Customer", "password": "ExamplePass!2026", "confirmPassword": "ExamplePass!2026" }`.
- SELLER requires `shop`: `{ "name": "Test shop", "description": "ร้านอาหารอีสาน ส้มตำ ลาบ ไก่ย่าง", "categoryIds": ["1", "2"], "address": {"line1":"123 Test Road","province":"กรุงเทพมหานคร","district":"ปทุมวัน","subDistrict":"ลุมพินี","postcode":"10330"}, "latitude": 13.75, "longitude": 100.5, "openingHours": {"days":["MON","TUE","WED","THU","FRI"],"open":"08:00","close":"18:00","timeZone":"Asia/Bangkok"}, "sizeClass": "SMALL" }`. Name max 200, description trimmed1–2000 required, categoryIds 1–10 unique positive decimal ID strings from GET /categories, address.line1 max 500, province/district/subDistrict max 100, postcode empty or 5 ASCII digits, opening hours structured days/time; all nonempty. Coordinates must be finite JSON numbers in latitude [-90,90], longitude [-180,180]. Size SMALL/MEDIUM/LARGE. Atomic nested creation of user + shop, shop name used as displayName; owner derived from new user; PENDING set by server. Opening hours stored as structured JSON.
- GOVERNMENT needs no extra profile fields; display name defaults to username.

201: `{ "user": { "id": "4", "role": "SELLER", "displayName": "Test shop" } }`; 400 invalid/missing role details; 409 duplicate identifier. ACTIVE account created; no JWT, password hash or wallet returned.

## Wallet and one-time payment requests

- `GET /wallets/me` (CUSTOMER/SELLER): returns `{role,balance,help,helpMonthlyLimit,month,testActionsEnabled}`. CUSTOMER access lazily creates CASH/BASE wallets and the idempotent THB 1,000 allocation for the current Asia/Bangkok month; `help` sums only that month's entries, so unused prior-month help does not carry forward. SELLER gets CASH only. Money values are decimal strings.
- `POST /wallets/top-up` (CUSTOMER): header `Idempotency-Key` plus `{amount:"500.00"}` adds a simulated CASH credit; retrying the same key returns the same resulting balance without another credit. `POST /wallets/help/reset` is available only when non-production and `ENABLE_TEST_WALLET_ACTIONS=true`; it appends the positive or negative adjustment needed to make current-month help exactly `1000.00`. `GET /wallets/history` returns up to 100 role-owned items; payment ledger rows are grouped by payment request and include `helpAmount`/`customerAmount`.
- `POST /seller/payment-requests` (SELLER): `{amount:"100.00"}` requires a seller-owned shop and creates a PENDING UUID request expiring in 15 minutes; response includes `scanPayload` and `expiresAt`. `GET /seller/payment-requests` lists the seller's recent requests with derived EXPIRED state. `POST /seller/payment-requests/:id/cancel` changes an owned pending request to CANCELLED.
- `GET /payment-requests/:id` (CUSTOMER) returns status and `{targetHelpAmount,helpAmount,customerAmount,canPay}`. Target government help is 60% rounded half-up to satang; actual help is `min(targetHelpAmount,currentMonthHelp)` and customer CASH pays the remainder. Insufficient/zero help therefore falls back to customer CASH instead of rejecting the payment.
- `POST /payment-requests/:id/pay` (CUSTOMER) settles once atomically, rejects only if CASH cannot cover `customerAmount`, credits seller CASH 100%, creates a linked SUCCEEDED purchase and marks the request PAID. Concurrent scans serialize on request/wallet rows; paid, cancelled or expired requests return 409. QR image/camera decoding is not part of the API; the UUID is the payload.
- All routes require Bearer auth; role mismatch is 403, malformed amount/token is 400, missing request/shop is 404. Coin awards and refunds are not included in this slice. Web `/api/wallet` is the same-origin HttpOnly-cookie proxy used by the customer/seller UI.
