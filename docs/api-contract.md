# Authentication contract (F02)

POST /auth/login: JSON `{ "username": "0000000000000", "password": "...", "role": "CUSTOMER" }`. Roles: CUSTOMER, SELLER, GOVERNMENT. Customer username must contain exactly 13 ASCII digits; other usernames are 1–255 characters. Password 1–1024 characters.

200: `{ "accessToken": "<JWT>", "expiresIn": 3600, "user": { "id": "1", "role": "CUSTOMER", "displayName": "..." } }`. 400 invalid input; 401 incorrect credentials, inactive account or role mismatch; 503 missing JWT configuration. IDs are strings. Login responses must not be cached.

GET /me: `Authorization: Bearer <JWT>`. 200 user profile with id, role, displayName; 401 missing/invalid/expired token or inactive account/changed role.

Web POST /api/auth/login forwards login to API and sets session cookie (HttpOnly, SameSite=Lax, Secure in production, 3600 seconds). Returns destination /wallet, /store or /government. Web POST /api/auth/logout returns 200 JSON `{ "message": "Logged out" }` and clears cookie; signed JWT expires naturally (no server revocation). Both require same-origin Origin header. Configure server-only API_URL for web and DATABASE_URL/JWT_SECRET for API.

Accounts use scrypt hashes documented in decisions.md. Demo seed credentials are documented in Test.md.

## Registration

POST /auth/register: common fields `role`, `username`, `password`, `confirmPassword`. Customer username is 13 ASCII digits; seller/government username is 3–64 ASCII letters/digits/underscore/dot/hyphen. Password 8–128 characters and confirmation must match.

- CUSTOMER requires `firstName` (trimmed 1–100 chars) and `lastName` (1–99 chars); joined into users.display_name. Example: `{ "role": "CUSTOMER", "username": "0000000000001", "firstName": "Test", "lastName": "Customer", "password": "ExamplePass!2026", "confirmPassword": "ExamplePass!2026" }`.
- SELLER requires `shop`: `{ "name": "Test shop", "description": "ร้านอาหารอีสาน ส้มตำ ลาบ ไก่ย่าง", "categoryIds": ["1", "2"], "address": {"line1":"123 Test Road","province":"กรุงเทพมหานคร","district":"ปทุมวัน","subDistrict":"ลุมพินี","postcode":"10330"}, "latitude": 13.75, "longitude": 100.5, "openingHours": {"days":["MON","TUE","WED","THU","FRI"],"open":"08:00","close":"18:00","timeZone":"Asia/Bangkok"}, "sizeClass": "SMALL" }`. Atomic nested creation of user + shop, shop name used as displayName; owner derived from new user; PENDING set by server. Opening hours stored as structured JSON.

## Government store approval

- `GET /government/stores?status=PENDING|APPROVED|SUSPENDED|REJECTED|ALL` (GOVERNMENT) returns up to 200 shops with owner, categories, address, coordinates, opening hours, status and latest review audit. Without `status`, all statuses are returned. `GET /government/stores/:id` returns one shop.
- `PATCH /government/stores/:id` (GOVERNMENT) accepts exactly `{ "status": "APPROVED" }` for a PENDING shop, or `{ "status": "SUSPENDED", "reason": "..." }` for a PENDING/APPROVED shop. Suspension reason is trimmed, required and at most 500 characters. The server stores reviewer ID and timestamp. APPROVED shops are discoverable through `GET /stores` and may create/settle seller payment requests; suspended shops are excluded and outstanding QR requests cannot settle.
- 400 invalid ID/filter/body, 401 missing/invalid authentication, 403 non-government role, 404 unknown shop, 409 invalid/already-applied transition. IDs are decimal strings. Web uses same-origin `/api/government/stores` proxies; mutations require same-origin `Origin`.

## Wallet and one-time payment requests

- `GET /wallets/me` (CUSTOMER/SELLER): returns `{role,balance,help,helpDailyRemaining,helpDailyLimit,helpMonthlyLimit,month,coins,testActionsEnabled}`. CUSTOMER access lazily creates CASH/BASE wallets and the idempotent THB 1,000 allocation for the current Asia/Bangkok month; `help` is the remaining monthly amount and `helpDailyRemaining` is the lesser of that amount and the remaining THB 200 Asia/Bangkok daily allowance. Unused prior-month help does not carry forward and unused daily allowance does not increase another day's limit. SELLER gets CASH only and help fields are null. Money values are decimal strings.
- `POST /wallets/top-up` (CUSTOMER): header `Idempotency-Key` plus `{amount:"500.00"}` adds a simulated CASH credit; retrying the same key returns the same resulting balance without another credit. Test-only `POST /wallets/help/reset-daily` clears today's Asia/Bangkok usage counter without changing the monthly balance, while `POST /wallets/help/reset` adjusts current-month help to exactly `1000.00`; both require non-production and `ENABLE_TEST_WALLET_ACTIONS=true`. `GET /wallets/history` returns up to 100 role-owned items; payment ledger rows are grouped by payment request and include decimal-string `helpAmount`/`customerAmount`/`rewardAmount`. A CUSTOMER payment with a non-reversed Coin ledger entry additionally includes integer `coinsEarned`; missing, ineligible or reversed awards omit the field. The UI groups these server rows by Asia/Bangkok day and distinguishes income with a green plus and expense with a red minus without recalculating financial or Coin rules.
- `POST /seller/payment-requests` (SELLER): `{amount:"100.00"}` requires a seller-owned shop and creates a PENDING UUID request expiring in 15 minutes; response includes `scanPayload` and `expiresAt`. `GET /seller/payment-requests` lists the seller's recent requests with derived EXPIRED state. `POST /seller/payment-requests/:id/cancel` changes an owned pending request to CANCELLED.
- `GET /payment-requests/:id` (CUSTOMER) returns status and `{targetHelpAmount,helpAmount,customerAmount,canPay}`. Target government help is 60% rounded half-up to satang; actual help is `min(targetHelpAmount,currentMonthHelp,currentDayHelp)` and customer CASH pays the remainder. Insufficient/zero help therefore falls back to customer CASH instead of rejecting the payment.
- `POST /payment-requests/:id/pay` (CUSTOMER) settles once atomically, applies no more than THB 200 help per Asia/Bangkok day and no more than the current monthly help balance, rejects only if CASH cannot cover `customerAmount`, credits seller CASH 100%, creates a linked SUCCEEDED purchase and marks the request PAID. Concurrent scans serialize on request/wallet rows; paid, cancelled or expired requests return 409. QR image/camera decoding is not part of the API; the UUID is the payload.
- All routes require Bearer auth; role mismatch is 403, malformed amount/token is 400, missing request/shop is 404. Coin awards are defined below; refunds remain pending. Web `/api/wallet` is the same-origin HttpOnly-cookie proxy used by the customer/seller UI.

### F08 — Atomic QR Coin awards (2026-10-13)

- `GET /wallets/me` additionally returns `coins`: current Bangkok monthly period's SUM of unreversed coin entries, integer string (`"0"` if none), null for SELLER. Coins remain separate from all THB balances; Main Quest grants follow the policy below.
- `GET /payment-requests/:id` additionally returns `{coins:number,coinReason:string,coinRuleVersion:number|null}` as an advisory estimate. `POST /payment-requests/:id/pay` returns the same fields as the actual award. The server recomputes at confirmation time; preview can change at a cutoff or after another purchase.
- Frozen `shop_coin_rates` is selected by confirmation time in the half-open rate window. Use its rule's inclusive `minimum_purchase`; below minimum yields `0/BELOW_MINIMUM`. Missing frozen rate (including shops approved mid-round) yields `0/NO_RATE`, payment still succeeds and is not backfilled. Otherwise, any prior coin entry for this customer/shop across all months, including reversed awards, selects repeat rate (`REPEAT_CUSTOMER`); no prior award selects new rate (`NEW_CUSTOMER`). Successful purchases with no award do not consume the first award. Visited status remains based on successful purchases independently.
- Purchase rule_id and coin entry rule_id match the frozen rate; award timestamp equals confirmed_at. Monthly period is lazily created at Bangkok boundaries as DRAFT with zero quest budget if absent, leaving existing configured periods unchanged. Coins, purchase, money transfer and QR status commit together in the existing Serializable transaction; any failure rolls back all. One coin entry per purchase and unique purchase idempotency key are enforced by existing DB constraints. Reusing PAID/cancelled/expired QR or losing a serialization/deadlock/unique race returns 409; a still-PENDING request can be retried. No extra Idempotency-Key header is required for QR pay: request UUID is the settlement key.
- Web scan confirmation displays the estimate and why it is zero; success toast uses the actual award. `/wallet` displays the actual current-month Coins total. Main Quest is live as documented below; customer monthly purchase history remains a preview and refunds remain pending.

## F06 — Automatic shared shop Coin rates

POST /government/coin-rules/generate-rates (GOVERNMENT Bearer, non-production only): JSON empty object `{}`. 200 `{periodId:string,startsAt:ISO,endsAt:ISO,created:boolean,shopCount:number}`; an existing round returns created=false and the stored count without mutation. 400 nonempty/invalid body, 401 missing/invalid auth, 403 other roles or production, 409 no rule effective at round start, conflicting existing interval or overlapping period. Server selects the current half-open 06:00/18:00 Asia/Bangkok round; callers cannot supply timestamps, rates or rule IDs. Web POST /api/government/coin-rules/generate-rates uses HttpOnly session and requires same-origin Origin. UI has pending/confirmation/Sonner and reloads actual stored rates. Manual button is exposed only when manualGenerationEnabled=true.

API startup and a 60-second interval ensure the current round when ENABLE_AUTO_COIN_RATES is not false. API uptime is required; restart catches up only the current round. With no effective rule the worker retries without creating a period, with a sanitized warning once per round. Generation shares advisory transaction lock 726031 with rule writers, and atomically inserts the period and all APPROVED shops selected at generation time. Once created, even an empty round is immutable; later-approved shops join next round. Multiple instances/manual requests reuse the winner.

For the rule effective at startsAt, sales window is [startsAt - sales_window_days, startsAt). Sum Decimal total_amount for purchases confirmed in that window and still SUCCEEDED or REFUNDED at/after startsAt; exclude refunds before cutoff and PENDING/FAILED. Award minimum does not filter shop sales. For newly generated rounds, new-customer Coins = ceil(new_low_sales_coins - (new_low_sales_coins - new_other_coins) * clamp(sales, 0, low_sales_threshold) / low_sales_threshold), using Decimal arithmetic. Zero sales gives the maximum, at/above threshold gives the minimum; threshold=0 uses the minimum without division. For 10→5 and threshold10000: sales0/2500/5000/7500/10000 yield10/9/8/7/5. Repeat Coins unchanged. Existing frozen rounds retain their stored rates from the previous binary calculation; never recalculate them. Store repeat_coins, rule_id, sales total and window in shop_coin_rates. Locked rows never recalculate after later purchases/refunds. Partial-refund policy is deferred; no award/eligibility/quest behavior changes here.

Opt-in PostgreSQL verification: from repo root set RUN_COIN_RATES_DB_TESTS=true then run `pnpm --filter api exec vitest run src/coin-rules/coin-rates.db.spec.ts`. Uses TEST_DATABASE_URL or configured DATABASE_URL, migrates a randomly named temporary schema and drops only that schema; never uses application tables for test records.

## F08/F09 — Live monthly Main Quest (2026-10-13)

- `GET /quests/me?month=YYYY-MM`: authenticated CUSTOMER only; default current Asia/Bangkok month, restricted to the latest 12 months. 200 `{month,months:string[],coins:integer-string,target:100,remainingCoins:number,rewardAmount:"100.00",status,canClaim:boolean,reward:null|{amount,used,available,expired,grantedAt,expiresAt}}`. All amounts are decimal THB strings, timestamps ISO. Status is IN_PROGRESS, WAITING_BUDGET, AVAILABLE, USED, EXPIRED or ENDED. GET never grants money. 400 invalid/out-of-range month; 401 unauthenticated; 403 other roles.
- `POST /quests/me/claim`: authenticated CUSTOMER, no request fields. 201 same projection for the current month. Safe to repeat; grants at most once per user/month, and does nothing while target/budget eligibility is unmet. 401/403 auth/role; 409 concurrent transaction conflict, retry safely. BFF GET `/api/wallet?action=quest&month=YYYY-MM` and same-origin POST `/api/wallet` `{action:"claimQuest"}` forward the HttpOnly session.
- Successful QR settlement automatically checks the current month's unreversed Coins after writing the award. At 100 Coins, allocate 100 THB only if the period is OPEN, within its Bangkok interval and its budget minus all grants covers 100 THB. Missing/DRAFT/CLOSED/exhausted budgets never create funds. A later claim or successful payment can retry while the same month is active. Coins are not deducted; excess Coins do not earn additional grants or carry to the next month.
- User/period row locks, Serializable transaction, unique user/month grant and unique allocation key prevent duplicate allocation and budget overspend. Grant, REWARD wallet credit, purchase/Coins/money and PAID transition commit atomically. No schema changes. Expiry is derived from immutable ledger and expires_at; historical rows are retained.
- QR preview/pay add `rewardAmount` (decimal string). Apply existing base help rules first, then available unexpired Main Quest reward to the remaining cash share, then CASH. The sum helpAmount + rewardAmount + customerAmount equals total. Newly earned rewards start with the next purchase; the earning purchase cannot spend its new grant. Reward debits link to both grant and purchase; zero debits are omitted. History purchase rows optionally include rewardAmount; REWARD_ALLOCATION is visible in the money history.
- `/wallet/quests` reads real monthly Coins and grant ledger, supports month selection, refresh/retry, claim retry, progress, used/available/expired amounts and Bangkok expiry. Completed live wallet/scan/top-up/explore and seller receive/history pages omit the Preview badge; customer purchase history and account/settings fixtures retain it. Refund reversal remains pending.
