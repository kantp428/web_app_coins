# ฐานข้อมูลไทยช่วยไทยพลีส

> เอกสารนี้เป็น blueprint จากงานเอกสารเดิม ยังไม่ใช่ Prisma migration ของ monorepo นี้ คำสั่งด้านล่างอ้างถึง `01-core.sql` และ `02-rewards.sql` ซึ่งไม่ได้อยู่ในโฟลเดอร์นี้; อย่ารันกับฐานข้อมูลแอปจนกว่าจะทบทวนและแปลงเป็น migration ตาม `PLAN.md`

ออกแบบเป็น **PostgreSQL 16+** เพราะโครงการยังไม่ระบุ DBMS ใช้ฐานข้อมูลเดียว แบ่ง SQL ตามภาพ ER สองภาพ เป็นแบบสร้างฐานข้อมูลใหม่ ไม่ใช่ migration สำหรับข้อมูลเดิม

## รายงาน FR-G03

```sql
SELECT month_key, budget_limit, granted_amount, unallocated_budget,
       gross_used_amount, refunded_amount, actual_expense,
       available_remaining, expired_unused, budget_not_spent, calculated_at
FROM v_main_quest_monthly_expenses
ORDER BY month_key;
```

| คอลัมน์ | ความหมาย (บาท) |
| --- | --- |
| budget_limit | งบ Main Quest ของเดือน |
| granted_amount | วงเงินที่มอบ ไม่ใช่ค่าใช้จ่ายจริง |
| unallocated_budget | งบตั้งต้น − วงเงินที่มอบ |
| gross_used_amount | ยอดตัดจ่ายจากรางวัลก่อนคืนเงิน |
| refunded_amount | ยอดคืนเงินเข้ารางวัลเดิม |
| actual_expense | ยอดใช้สุทธิ = ยอดตัดจ่าย − ยอดคืนเงิน |
| available_remaining | วงเงินมอบแล้วที่ยังใช้ได้ก่อนหมดอายุ |
| expired_unused | วงเงินมอบแล้วที่ยังไม่ใช้ แต่หมดอายุแล้ว |
| budget_not_spent | งบตั้งต้น − ยอดใช้สุทธิ รวมส่วนที่ยังผูกพันกับวงเงินผู้ใช้ จึงไม่ใช่งบที่ออกสิทธิ์เพิ่มได้ทั้งหมด |

รายงานรวมรายการเงินต่อ grant ก่อนรวมต่อเดือน ป้องกันวงเงินถูกนับซ้ำจากหลายรายการซื้อ เดือนที่ตั้งไว้แต่ไม่มีรางวัลแสดงยอดศูนย์ `month_key` คือวันแรกของเดือน ตัดรอบ Asia/Bangkok รวมต้นรอบแต่ไม่รวมปลายรอบ เงินใช้ `numeric` ไม่ใช้ floating point

สมการตรวจสอบ: `granted_amount = actual_expense + available_remaining + expired_unused` และ `budget_limit = unallocated_budget + granted_amount` ตัวอย่าง งบ 1,000 มอบ 200 ใช้ 70 คืน 20: ใช้สุทธิ 50 งบยังไม่จัดสรร 800 วงเงินคงเหลือ 150; เมื่อหมดเดือน 150 ย้ายไปยอดหมดอายุ ไม่เพิ่มค่าใช้จ่าย

เดือนรายงานเป็น **เดือนที่มอบรางวัล** คืนเงินข้ามเดือนแล้วปรับยอดเดือนต้นทาง ยอดคืนไม่ต่ออายุสิทธิ์ ไม่ใช่รายงานกระแสเงินสดตามวันที่คืนหรือ snapshot ณ วันปิดบัญชี รายงานคำนวณจากข้อมูลปัจจุบันพร้อม `calculated_at`

`v_main_quest_grant_balances` แสดงยอดต่อรางวัล, `v_monthly_coin_progress` รวม Coins สุทธิรายคน/เดือน (ไม่มีแถวให้ตีความเป็น 0) และ `v_wallet_balances` แยกเงินสด สิทธิพื้นฐาน และรางวัลที่ยังไม่หมดอายุ

## ข้อกำหนดก่อนพัฒนา Backend

SQL นี้เป็น DDL และ read views มี PK, FK, UNIQUE, CHECK และ index แต่ **ยังไม่บังคับกฎข้ามแถวทั้งหมดด้วย trigger/procedure** ต้องทำรายการต่อไปนี้ใน transaction เดียวกันและไม่อนุญาต client เขียนตารางโดยตรง:

1. ตรวจบทบาท/เจ้าของข้อมูล สถานะผู้ใช้ ร้าน และกระเป๋า เก็บรหัสผ่านเป็น hash จำกัด view รายคนให้เจ้าของข้อมูล รัฐอ่านรายงานรวม
2. ล็อกเดือนด้วย `SELECT ... FOR UPDATE` ก่อนออกสิทธิ์ ตรวจเดือน OPEN และเวลาอยู่ในรอบ รวม Coins ที่ไม่ถูกถอนให้ครบ 100 ตรวจงบยังไม่จัดสรรไม่น้อยกว่า 100 แล้วสร้าง grant และ REWARD_ALLOCATION +100 พร้อมกัน UNIQUE `(user_id, period_id)` กันรับซ้ำ ทุกเส้นทางที่ลดงบต้องใช้ lock เดียวกันและห้ามลดงบต่ำกว่ายอดมอบ
3. ล็อก wallet และ grant ก่อนจ่าย/คืนเงินด้วยลำดับเดียวกันทุกคำขอ ตรวจวันหมดอายุและยอดไม่ติดลบ แยก PURCHASE ติดลบตาม CASH/BASE/REWARD ให้ตรงสามส่วนใน purchases ห้ามใช้รางวัลที่เกิดจากรายการซื้อเดียวกันย้อนหลังมาจ่ายรายการนั้น
4. ยืนยันการชำระก่อนเปลี่ยนเป็น SUCCEEDED และให้ Coins ตรวจยอดขั้นต่ำ กติกาที่มีผล ช่วงประเมินยอดขาย และประวัติลูกค้า ณ เวลาซื้อ awarded_at ต้องอยู่ในเดือนที่อ้างอิง การดูแผนที่ไม่ให้ Coins รุ่นกติกาต้องไม่ทับช่วงกันและรุ่นที่ใช้งานแล้วห้ามแก้/ลบ
5. รองรับ **คืนเงินเต็มจำนวนครั้งเดียวต่อรายการ** สร้าง REFUND กลับแต่ละแหล่งเท่ากับ PURCHASE เดิม เปลี่ยน purchase เป็น REFUNDED และตั้ง reversed_at พร้อมกัน ไม่ลบประวัติ หากคืนเข้ารางวัลหลังหมดอายุให้ลง EXPIRY เท่ากับยอดคืนเพิ่มใน transaction เดียวกัน view จะไม่เปิดวงเงินนี้ให้ใช้
6. สมมติฐานเมื่อ Coins ต่ำกว่า 100 หลังคืนเงิน: คงสิทธิ์ที่เคยมอบ ไม่เรียกเงินคืนและไม่ให้รางวัลเดือนเดิมซ้ำ เพื่อไม่สร้างยอดติดลบจากเงินที่ใช้แล้ว ต้องทบทวนนโยบายก่อนใช้งานจริง การคืนบางส่วน/เพิกถอนสิทธิ์ยังไม่รวมในแบบนี้
7. เก็บ idempotency key เดิมเมื่อ retry และเทียบ payload เดิม ห้ามใช้ key เดิมกับรายการต่างกัน รายการเงินเป็น append-only ต้องจำกัดสิทธิ์ UPDATE/DELETE ด้วย Backend หรือ DB role
8. งานสิ้นเดือนลง EXPIRY สำหรับ reward ledger ที่เหลือโดยล็อก grant เช่นเดียวกับการจ่าย/คืนเงิน ป้องกันลงซ้ำด้วย key คงเดิม ยอดรางวัลใน view ตัดอายุตามเวลาแม้งานนี้ล่าช้า เปิดเดือนใหม่โดยสร้าง monthly_periods ไม่ลบประวัติหรือแก้เงินสด

ภาพเดิมยังไม่แก้ ดูรายการใน `DIAGRAM-NOTES.md` ใช้ SQL เป็นฉบับอ้างอิงใหม่

## การตรวจสอบ

ตรวจไวยากรณ์ทั้งสองไฟล์ด้วย PostgreSQL parser (pglast) แล้ว ทดสอบสูตร view ด้วย `python scripts/check_main_quest_views.py` ครอบคลุมเดือนว่าง หลายรายการซื้อ การคืนเงิน การตัดสิทธิพื้นฐานออกจากรายงาน เวลาหมดอายุ และคืนเงินข้ามเดือน การทดสอบสูตรใช้ SQLite รัน SELECT จากไฟล์จริง ไม่ใช่การทดสอบ DDL/FK บน PostgreSQL server; ยังต้องทดสอบการติดตั้งจริงและ transaction พร้อมกันก่อนใช้งาน
